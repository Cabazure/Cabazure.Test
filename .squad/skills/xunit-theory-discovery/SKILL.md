## Context

When implementing custom xUnit 3 `DataAttribute` classes that use AutoFixture to generate test arguments, VS Test Explorer may show tests as "Not Run" even when the test runs successfully. This is caused by a mismatch in `TestCaseUniqueID` between discovery and execution phases.

## Root Cause

xUnit 3's `DataAttribute` contract includes `bool SupportsDiscoveryEnumeration()`:

- When `true`, xUnit calls `GetData()` **twice**: once at discovery (to populate Test Explorer), once at execution (to run the test)
- VS Test Explorer matches test cases by `TestCaseUniqueID`, which is a **SHA256 hash of the serialized argument values** (not the display name)
- AutoFixture generates **non-deterministic values** on every call (e.g., `paramName + Guid.NewGuid()`)
- Different argument values → different SHA256 hash → different `TestCaseUniqueID` → VS Test Explorer cannot match discovery case to execution case → "Not Run"

Confirmed via decompilation of `xunit.runner.visualstudio` 3.1.5:
- `TestCaseUniqueID` is computed from serialized arguments (not display name)
- VS derives `TestCase.Id` from `TestCaseUniqueID` for matching

## Patterns

### Correct Implementation (AutoFixture-Backed Attributes)

```csharp
public class AutoNSubstituteDataAttribute : DataAttribute
{
    public override bool SupportsDiscoveryEnumeration() => false;

    public override ValueTask<IReadOnlyCollection<ITheoryDataRow>> GetData(
        MethodInfo testMethod,
        DisposalTracker disposalTracker)
    {
        // AutoFixture generates values here — must return false above
        // to prevent double invocation with different values
    }
}
```

**Key:** Return `false` for ANY data attribute where `GetData()` produces non-deterministic values (AutoFixture, random generators, `Guid.NewGuid()`, `DateTime.Now`, etc.).

### Why Alternatives Don't Work

#### ❌ Setting `Label` or `TestDisplayName`

```csharp
// DOES NOT FIX THE ISSUE
return new TheoryDataRow(value1, value2)
{
    TestDisplayName = "Stable Name",
    Label = "Stable Label"
};
```

**Why:** `Label` and `TestDisplayName` affect only the **display string** shown in Test Explorer, NOT the `TestCaseUniqueID` used for matching. The ID is always computed from serialized argument values.

#### ❌ Deterministic Seeding

```csharp
// TECHNICALLY WORKS, BUT WRONG
var fixture = new Fixture();
fixture.RepeatCount = 1; // Same seed every time
```

**Why:** Violates AutoFixture's core value proposition (randomization catches edge cases). If deterministic values are needed, use `[InlineAutoNSubstituteData]` or `[MemberAutoNSubstituteData]` with explicit values.

#### ❌ `SupportsDiscoveryEnumeration() => true` for Member/Class Attributes

Even when leading parameters are user-provided (deterministic), trailing AutoFixture-generated parameters are still non-deterministic:

```csharp
[MemberAutoNSubstituteData(nameof(Inputs))]
public void Test(int userValue, string autoGenerated) // ← autoGenerated breaks ID stability
```

**No xUnit API exists** to exclude trailing parameters from `TestCaseUniqueID` hash. All arguments contribute to the ID.

## Anti-Patterns

### ❌ Returning `true` Because "Discovery is Faster"

```csharp
public override bool SupportsDiscoveryEnumeration() => true; // WRONG for AutoFixture
```

**Problem:** Tests appear in Test Explorer before first run but show "Not Run" after execution.

**Fix:** Return `false`. Tests appear in Test Explorer *after* first execution, but they run correctly and match on subsequent runs.

### ❌ Mixing Deterministic and Non-Deterministic Sources

```csharp
// If ANY argument is non-deterministic, SupportsDiscoveryEnumeration MUST be false
public override ValueTask<IReadOnlyCollection<ITheoryDataRow>> GetData(...)
{
    var deterministicValue = 42;
    var nonDeterministicValue = fixture.Create<string>(); // ← Makes entire row unstable
    return new TheoryDataRow(deterministicValue, nonDeterministicValue);
}
```

## Trade-Offs

**Accepting:** Single theory entry before first run; each row appears after execution.  
**Gaining:** Test correctness — cases run and match properly.

**Architectural Principle:** Test correctness trumps IDE discoverability.
